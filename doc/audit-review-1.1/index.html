Read first: one figure changed on purpose. The reviewer reconciled the e-wallet at ₱12,000. That ₱18,000 deduction could not be produced by the BR-11 formula, and its rescue (RSC-000020) was missing from the rescue list. RSC-000020 now exists with a full breakdown that totals ₱18,048.80, so the balance is now ₱30,000 − ₱18,048.80 = ₱11,951.20. Due dates and contract dates also moved by one day; see the “Data fixed” rows under Invoices.

How to verify (step by step)

  1. In frontend-portal, run npm run typecheck, npm test and npm run build. All three must pass.
  2. Run npm run dev and open the sign-in page. The mock DB is now version 13, so saved demo data reloads once on first load. If a browser still shows old data, sign out and reload.
  3. Sign in as client@abclogistics.ph / Demo@2026 (Active client). Work through the sections below and compare each screen with the After screenshot.
  4. Sign in as client@pacificmovers.ph (ON HOLD) to check the blocked states: dashboard banner, disabled Create EWA / Request rescue, negative e-wallet.
  5. Choose Vendor / supplier and sign in as vendor@tirepro.ph for the vendor portal.
  6. Arithmetic to re-check: Unpaid ₱47,040 + ₱27,040 + ₱5,040 = ₱79,120. Rescue RSC-000020: 2,000 + 12,650 = 14,650 → +10% = 16,115 → +12% VAT = 18,048.80. Wallet: 30,000 − 18,048.80 = 11,951.20. Amber threshold: 10,000 × 125% = 12,500. Due date: invoice date + 30 days (e.g. 13-Oct → 12-Nov).

Dates in the demo are relative to “today”, so the exact days you see will differ from these screenshots (taken 02-Nov-2026). The relationships between them stay the same.
